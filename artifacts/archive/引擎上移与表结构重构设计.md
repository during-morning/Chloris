# Chloris — 引擎上移（A0/A2/A3）与表结构重构（S7/S8）设计

## 1. 目标形态

```
┌──────────────────────────────────────────────────────┐
│ 服务端进程（原生端内嵌，dart:io + shelf + drift）      │
│   规则引擎 · 网络抓取 · JS 运行时 · SQLite              │
│   HTTP API：见 §2                                       │
└──────────────────────────────────────────────────────┘
        ▲                                  ▲
        │ 同进程调用                        │ HTTP（token）
┌───────┴────────┐              ┌──────────┴─────────┐
│ 原生 UI         │              │ Web UI（纯渲染）    │
└────────────────┘              └────────────────────┘
```

Web 端**不含**引擎、不含本地数据库、不含 CORS 代理。没连上服务端就不可用（已确认决策）。

## 2. A2 — API 扩容

### 2.1 契约（A0，已实现）

`api_contract.dart` 已声明：

- `chlorisApiVersion = 1`，客户端拒绝版本不匹配的服务端，而不是错误解码
- `ChlorisApiRoute`：26 条路由的 method + path 单一事实来源
- `ApiEnvelope { isSuccess, data, errorMsg, stage, retryable, suggestedAction }`
  —— 保留 Legado 的 `isSuccess/errorMsg` 线格式，额外承载 `DomainError` 的
  stage / retryable / suggestedAction，让 UI 能渲染阶段与恢复动作
- `ServerInfo { apiVersion, appVersion, capabilities }` —— `/version` 返回，
  **故意不鉴权**：客户端必须在拿到 token 之前就能发现版本不匹配
- `ChapterListQuery` / `BookContentQuery` / `BookProgressBody` 三个具体请求模型

### 2.2 路由对照

| 能力 | Legado-E | Chloris 现有（9） | A2 需要 |
|---|---|---|---|
| 书源 CRUD | `/getBookSource(s)` `/saveBookSource(s)` `/deleteBookSources` | ✅ 全部 | — |
| 书架 | `/getBookshelf` `/saveBook` `/deleteBook` | ❌ | ➕ 3 |
| 进度 | `/saveBookProgress` | ❌ | ➕ 1 |
| 本地书导入 | `/addLocalBook` | ❌ | ➕ 1 |
| 目录 | `/getChapterList` `/refreshToc` | ❌ | ➕ 2 |
| 正文 | `/getBookContent` | ❌ | ➕ 1 |
| 封面 / 图片 | `/cover` `/image` | ❌ | ➕ 2 |
| 阅读配置 | `/getReadConfig` `/saveReadConfig` | ❌ | ➕ 2 |
| 替换规则 | `/getReplaceRules` `/saveReplaceRule` `/deleteReplaceRule` `/testReplaceRule` | 部分（有 get/test） | ➕ 2 |
| RSS 源 | `/getRssSource(s)` `/saveRssSource(s)` `/deleteRssSources` | ❌ | ➕ 5 |
| 版本探测 | — | ❌ | ➕ 1（Chloris 新增） |
| WebSocket 调试 | `/bookSourceDebug` `/rssSourceDebug` `/searchBook` | 仅 `bookSourceDebug`（且无鉴权） | ➕ 2 + 补鉴权 |
| **合计** | 21 | 9 | **需新增 17 条** |

### 2.3 处理器设计约束

1. **每个处理器只做协议转换**，业务逻辑走已有 UseCase（`OnlineBookPort` /
   `ChapterCatalogStore` / `ChapterContentStore` / `RssFeedPort` 等）。服务端不得出现
   第二套抓取实现。
2. **错误统一走 `ApiEnvelope.failure(DomainError)`**，禁止把原始异常字符串直接返回。
3. **大响应流式输出**（Legado 在列表 > 3000 项时用 `okio.Pipe` 分块）。书架与目录列表
   需要同样处理，否则一次 `/getBookshelf` 会构造整个字符串。
4. **`/image` `/cover` 走二进制**，不套 JSON envelope。

## 3. A3 — Web 端重做

### 3.1 要删除的

| 目标 | 理由 |
|---|---|
| `chloris/lib/engine/js_runtime/js_runtime_web.dart` | 浏览器 `eval` 运行时整体消失；JS 只在服务端一处执行，沙箱与超时只需实现一次 |
| `/proxy/http`、`/proxy/bytes`、`proxyImage` | 引擎上移后浏览器不再直连外站，CORS 代理没有存在理由 |
| Web 端对 `AppDb` / `BlobStore` / `KvSettings` 的写入路径 | Web 不再拥有本地权威存储 |

### 3.2 要替换的

| 现有 | 替换为 |
|---|---|
| `OnlineBookPort` 的引擎实现 | `HttpOnlineBookPort`（走 §2 契约） |
| `TocCache.instance` | 服务端 `/getChapterList`（客户端只保留内存 LRU） |
| `ChapterTextCache.instance` | 服务端 `/getBookContent` |
| `ChapterCatalogStore` 等 Port | 保持接口不变，只换 Adapter —— 这是现有分层带来的直接收益 |

**关键点**：应用层与 UI 层**不需要改**，因为界面已经依赖 Port 而非引擎。A3 的实际改动
集中在 `lib/engine/` 与 `lib/core/persist/` 的条件导入边界。

### 3.3 新增的客户端状态

- `ServerAvailability { unreachable, versionMismatch, ready }`（已在契约中声明）
- 断线重连与"服务端未启动"的用户可见状态
- token 配对入口（`WebServiceStatus.token` 已暴露，A1 完成）

## 4. S7 — 表结构设计

### 4.1 补表顺序（按用户数据价值）

| 批次 | 表 | 关键约束（对齐 Legado） |
|---|---|---|
| ① | `BookChapter` | PK `(url, bookUrl)`；`UNIQUE(bookUrl, index)`；FK `bookUrl → Books.bookUrl ON DELETE CASCADE` |
| ② | `Bookmark` / `ReadRecord` | `Bookmark` PK `time`；`ReadRecord` PK `(deviceId, bookName)`；替代 KV 集合，消除整体重写丢更新 |
| ③ | `BookGroup` + `Books.type/group` 位掩码 | 位分配上限 64；8 个保留负 id（-1 全部 / -2 本地 / -3 音频 / -4 网络未分组 / -5 本地未分组 / -6 视频 / -11 更新失败） |
| ④ | `Cookie` / `Cache` | `Cookie` PK `url`；`Cache` PK `key` + `deadline` 语义（0 = 永不过期） |
| ⑤ | `RssSource` / `RssArticle` / `RssStar` / `RssReadRecord` | `RssArticle` PK `(origin, link, sort)`；`RssStar` PK `(origin, link)` |
| ⑥ | `ReplaceRule` 补齐列 | 补 `scope` / `excludeScope` / `isRegex` / `timeoutMillisecond`（当前 drift 表缺这 4 列且无人写入） |

### 4.2 位掩码查询的技术约束

drift 无内置 `&` 表达式，必须用 `CustomExpression` / `customSelect`。**并且不能在 Dart 层
先过滤再分页** —— Legado 的语义是 SQL 级位运算，例如：

```sql
-- BookDao.flowRoot
where type & 8 > 0 and type & 256 = 0
  and ((select sum(groupId) from book_groups where groupId > 0) & group) = 0
```

在 Dart 层过滤会改变分页结果与计数，必须原样下沉到 SQL。

### 4.3 `BookSourcePart` 视图

Legado 的 `book_sources_part` 是 `@DatabaseView`，含两个派生列
（`hasLoginUrl` / `hasExploreUrl`）。drift 支持 `View`，但**前提是标量列齐全** ——
当前 `BookSources` 只有 12 列，`loginUrl`/`exploreUrl` 埋在 `raw` JSON 里。
所以 S7 第 ⑥ 批必须先把 `BookSource` 的 32 列真正落表，视图才有意义。

### 4.4 分组匹配语义

Legado 用逗号边界匹配：

```sql
bookSourceGroup = :k or bookSourceGroup like :k||',%'
  or bookSourceGroup like '%,'||:k or bookSourceGroup like '%,'||:k||',%'
```

Chloris 现在是 `displaySourceGroup(s) == filter`。**实测后这条不是缺陷**：Chloris 的
`displaySourceGroup` / `unifySourceGroup`（`source_unify.dart:55,73`）会把原始分组
**重新归并为一组固定分区**（听书 / 漫画 / …），过滤比较的是归并后的分区名而不是逗号
列表，所以边界歧义（`A` vs `AB`）并不存在。此条从 S9 移除。

### 4.5 ⚠️ `UNIQUE(name, author)` 需要一个先决决策（实测发现）

原计划把 Legado 的 `books.UNIQUE(name, author)` 直接搬到 Chloris。实测后发现两侧的
**书架模型根本不同**，直接加约束会出错：

| | Legado | Chloris |
|---|---|---|
| 书架表 | `books`，**按 `(name, author)` 去重**，`origin` 指向选定源 | `onlineShelf`（KV），存 **`(BookSource, SearchBook)` 对** |
| 每源候选 | 独立的 `searchBooks` 表 | 无独立表，候选直接混在书架里 |
| 同一本书多个源 | 书架一行，候选在 `searchBooks` | 书架**多行**（`add` 只按 `bookUrl` 判重） |

也就是说 `onlineShelf` 语义上更像 Legado 的 `searchBooks`，而不是 `books`。直接加
`UNIQUE(name, author)` 只有两种结果，都不可接受：

1. 现有数据里若存在同名同作者的多源条目，**建索引直接失败**，迁移中断；
2. 先做去重再建索引，等于**静默删掉用户的书源候选**。

**S7 必须先决策书架模型**：是引入独立 `searchBooks` 表让 `books` 按身份去重（对齐
Legado），还是承认 Chloris 保留"一书多条目"并放弃该约束。这是建模决策，不是能顺手
加上的约束。决策前 S7 不应包含 `UNIQUE(name, author)`。

### 4.6 本轮已落地的位掩码修正（S9 部分）

`library_chrome.dart` 的本地/在线过滤此前用 `origin == BookType.localTag`，而模型里
早有基于位标志的 `Book.isLocal`（`type & local`，另含 `webDav::` 前缀）。后果是
**WebDAV 本地书被归到"在线"**。已改用 `Book.isLocal`，并补齐位值对照与
`fromSourceType` 的测试：`BookType` 的 9 个位值与 Legado `constant/BookType.kt` 逐一一致。

## 5. S8 — 迁移设计

### 5.1 原则

1. **KV 仍是迁移期的事实源**，表是新增的权威；一个版本内**双写**，读优先表。
2. **迁移幂等**：以 `chlorisSettingsSchemaVersion` + drift `schemaVersion` 双标记，
   可重复执行不产生重复行。
3. **可回滚**：旧 KV 键保留至少一个版本，回滚时读旧键仍可用。
4. **失败不半途**：整批导入放在一个事务里；失败则回滚并保留 KV。

### 5.2 步骤

```
1. drift schemaVersion 2 → 3：新建 ①-⑥ 批次表（只加表，不改现有列）
2. 一次性导入（幂等，单事务）：
     onlineShelf(KV)        → Books + BookSources + BookGroup
     readingProgressV1(KV)  → Books.dur*
     bookmarks(KV)          → Bookmark
     readRecords(KV)        → ReadRecord
     importedRssSources(KV) → RssSource
     rssArticleSnapshots    → RssArticle
     rssStars(KV)           → RssStar
     toc/<bookUrl> (blob)   → BookChapter
     replaceRules(KV)       → ReplaceRule
3. 双写：写路径同时更新 KV 与表（已有 PersistQueue 可复用）
4. 读切换：读优先表，表为空时回落 KV
5. 稳定一个版本后，删除 KV 键（独立提交，可单独回滚）
```

### 5.3 必须配套的 fixture

- 旧版 `legado.db`（89 版 schema）导入后的分组/位掩码解码
- KV 快照 → 表 → 导出的往返一致性
- 迁移中途失败后重跑不产生重复行
- 回滚：删除迁移后的表数据，旧 KV 仍能恢复完整书架与进度

**没有这些 fixture 之前不应执行 S8。** 这是全项目唯一会损坏用户数据的步骤。
