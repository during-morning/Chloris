## 1. 这份计划要解决的问题

书源规则是社区维护的第三方数据，一条规则本质上是一串告诉阅读器「去哪个地址、从页面里抠哪块内容」的指令。Chloris 用纯 Dart 重写了这套规则引擎，Legado-E 用的是 Kotlin + jsoup / Rhino。

用户能直接感知到的失败长这样：

- 搜索有结果，点进去某几章是空的。
- 目录里混进了「首页」「分类」「登录」这类站点导航。
- 翻到第 2 页，实际请求的是第 4 页。
- 某个源在 Legado 上正常，在 Chloris 上整源取不到内容（通常是需要鉴权）。
- 有的源干脆什么都没有，而且不报错——静默返回空。

这份计划的目标只有一句：**同一条规则，在 Chloris 和 Legado-E 上取到同样的内容。**

## 2. 现在已经能正常工作的部分

绝大多数书源规则在两侧结果一致。已经对齐的包括：

- 组合符 `&&` / `||` / `%%`、`@` 链、`@put` / `@get` / `{{}}` 变量与模板。
- `##匹配##替换` 替换后缀、四种模式前缀（CSS / XPath / JSONPath / 正则）。
- 结果算子 `@text` / `@html` / `@ownText` / `@textNodes` / `@attr`。
- CSS 主流选择器，含带引号与不带引号的 `:contains(...)`。
- JSONPath 的递归、切片、联合、通配、过滤；另外还支持 Legado 没有的 `=~` 正则与 `contains()`。
- 正则的链式语义。
- 词法层的引号与括号感知——这一层比 Legado-E 更严格，引号里的 `&&` 不会被误切。

顺带一提，Legado-E 自己有几处缺陷（例如 `@webjs:` 分支实际不可达、`@put` 里出现嵌套 `}` 会被截断），Chloris 已经修正。评估差距时这些不能算成 Chloris 落后，原始对照里有完整清单。

### 各子层当前估计

| 子层 | 估计 | 主要短板 |
| --- | ---: | --- |
| 变量与模板 | 88–95% | 大变量分层缺失；源级变量重启后丢失 |
| 执行内核 | 85–92% | 多值拼接的语义消歧；空规则 + 替换后缀 |
| 词法与编译 | 82–90% | 平衡组保护面与 Legado 不同 |
| 正则 | 80–90% | 默认编译标志与 Legado 不同 |
| CSS | 78–88% | 索引区间算法；属性值去重 |
| JSONPath | 75–88% | 缺函数扩展 |
| 请求构造 | 65–80% | 模板时序；请求头与 Cookie 优先级 |
| XPath | 55–70% | 缺一批函数；只处理元素节点 |
| JS 宿主 | 50–65% | 无共享作用域、沙箱与超时保护 |

综合来看：主流书源已进入可用区间，**XPath 与 JS 宿主是两个结构性短板**；请求构造是最隐蔽的分叉区——规则写得对，但请求发出去就错了。

## 4. 不在本轮范围内

以下内容属于目标边界，不是缺陷，不计划在这一轮解决：

- **Android 专有 JS 与 Rhino 沙箱**：Web 用浏览器 `eval`、移动端用 QuickJS，共享作用域与类白名单无法完全复现。
- **DRM、字体布局、系统 TTS**：纯 Dart / Web 目标下做不到等价。
- **社区书源自身失效**：站点改版导致的规则失效属于逐源校准，不是引擎缺陷。
